# ShopLens 开发规格

> 本文件是当前施工唯一事实来源。项目使用单 Agent StateGraph，覆盖真实商品导购、模拟下单，以及基于自然语言的订单查询与消费统计。

## 项目目标

基于 LangGraph 单 Agent，使用值得买 MCP 搜索真实商品，由 LLM 基于值得买返回字段做有证据约束的比较决策；用户选择并确认后，系统将模拟订单及商品快照写入本地 PostgreSQL。用户还可以在同一输入框中用自然语言查询历史订单或消费情况。

核心链路：

```text
商品导购：用户需求 → 多轮澄清 → 值得买商品搜索 → 候选事实整理 → LLM 对比决策 → 用户选择并确认 → 模拟订单落库

订单查询：自然语言输入 → 意图识别 → 时间/筛选条件解析 → 订单检索或消费聚合 → 订单卡片/统计摘要
```

## 范围

- 继续使用一个 LangGraph StateGraph；节点是单 Agent 内可追踪的流程步骤，不拆分为多 Agent。
- 当前产品只面向一个本地用户。系统不提供多用户隔离、租户切换、用户选择或跨用户查询能力；现有数据库字段如 `user_id` 仅按项目已有模型兼容使用，不作为本期功能入口。
- 商品候选只来自值得买真实源。可按品牌、品类、预算与用户指定商城筛选；商城筛选通过值得买支持的 `mall_id` 映射实现。
- 对搜索候选先做本地硬约束、预算过滤和去重，再将最多 3 个候选的值得买字段整理为紧凑证据上下文。
- LLM 负责比较用户偏好与已检索事实、给出首选和取舍理由；候选、金额、平台、属性和证据值始终由服务端数据提供。LLM 不能补造商品事实。
- 下单是演示用模拟订单，不跳转真实商城，不调用支付或真实交易接口。用户必须明确选择商品并确认后才落库。
- 支持输入“昨天我买了什么”“上周买了哪些商品”“最近 30 天买耳机花了多少钱”“今年在京东买了什么”等自然语言订单查询和消费统计。
- 订单查询结果复用现有订单信息卡片；统计结果使用结构化摘要展示订单数、总金额、平均客单价及可选的品类/平台分组。
- 保留指数退避重试、`CLOSED/OPEN/HALF_OPEN` 三态熔断、可选数据降级、OpenTelemetry/Langfuse Trace 与评测基线。
- 继续支持现有明确授权的用户偏好记忆；长期偏好与订单查询条件隔离，当前订单查询条件优先于长期偏好。

## 非目标

- 仿真京东/淘宝/拼多多报价、跨平台比价、SKU 跨源归一、优惠券/物流综合成本、下单前二次询价锁价。
- 值得买内容/评测全文检索、评论情感分析、反事实重排、降价提醒。
- 真实下单、支付、库存承诺或商城账号授权。
- 多用户账户、权限隔离、租户级订单空间、用户切换。
- 按订单号精确查询，例如不支持“查订单 202610200013943”；订单查询只按自然语言时间、关键词、品类和平台等条件检索。
- 为值得买未返回的字段编造参数级结论；缺失字段必须显示为未知。

## Agent 编排

同一个 StateGraph 根据意图进入不同流程：

1. `route`：识别 `shopping`、`order_search`、`order_summary`、`memory`、`other` 五类意图。
2. `clarify`：购物意图补全品类、预算、颜色、品牌等必要条件；订单意图只在时间范围或筛选条件确实无法确定时追问。
3. `retrieve`：通过值得买 MCP 搜索最多 5 条真实候选，传递可表达的品类、预算、品牌和 `mall_id`。
4. `recommend`：以结构化输出做候选比较，返回候选卡片、可核对的比较维度、首选（可为空）和逐项理由。
5. `confirm`：interrupt 等待用户选择候选并确认模拟下单；取消则结束本轮。
6. `place_order`：校验所选 SKU 仍属于本轮推荐，使用状态中的商品快照和幂等键写入 PostgreSQL。
7. `parse_order_query`：把订单查询文本转换为结构化时间范围、关键词、品类、平台和统计需求。
8. `query_orders`：调用订单检索能力返回订单明细；无结果时返回明确的空结果状态。
9. `summarize_orders`：对订单明细执行总金额、订单数、平均客单价以及品类/平台分组统计。

购物完成、取消或订单查询结束后，不得将上一轮候选、订单筛选条件或统计结论作为下一轮事实；长期偏好仍按显式记忆指令管理。

## 订单查询语义

### 支持的自然语言

- 时间：今天、昨天、前天、上周、上个月、最近 7 天、最近 30 天、今年、某个具体日期或日期范围。
- 筛选：商品关键词、品类、平台；例如“上个月买耳机”“今年在京东买了什么”。
- 查询类型：
  - 明细查询：买了什么、买过哪些商品、上次买的耳机是什么。
  - 统计查询：花了多少钱、买了几单、平均每单多少钱、按品类/平台统计。

时间解析使用半开区间 `[start_at, end_at)`，以应用时区 `Asia/Shanghai` 解释自然日期。当前日期由运行时注入；例如在 2026 年 10 月 21 日，“昨天”解析为 2026 年 10 月 20 日。

“上次购买”这类表达如果匹配多个候选或语义不明确，Agent 必须先澄清；不能让模型自行猜测。时间范围、关键词和平台均缺失且无法从上下文推断时，同样进入澄清状态。

### 查询工具分工

本地 Tool 负责确定性转换：

```text
resolve_time_range(text, now, timezone) -> {start_at, end_at, label}
normalize_order_query(text, parsed_time) -> {keyword, category, platform, query_type}
```

订单数据能力通过本地 FastMCP stdio 服务暴露为标准 MCP 工具，避免 Agent 直接拼接 SQL：

```text
search_orders(start_at, end_at, keyword?, category?, platform?)
summarize_orders(start_at, end_at, keyword?, category?, platform?, group_by?)
group_orders(orders, dimension)
```

MCP 服务内部复用现有订单仓储/SQLAlchemy 查询和 Decimal 聚合；服务不接收用户 ID 作为本期业务参数，默认查询当前本地用户的订单集合。工具返回结构化订单快照，不返回支付敏感信息。

## 商品事实与证据约束

### 值得买商品事实

保留当前 MCP 返回的 `title`、商品标识（若源提供）、`page_price`、商城、品牌、品类、促销信息、好评率、`price_tags`、图片和商品链接。只有源中实际存在且解析成功的字段进入事实集合；缺失价格的候选不可下单，缺失字段显示为未知而不是推断。

用户指定商城时使用配置化映射传 `mall_id`。当前已验证映射为京东 183、淘宝精选 243、拼多多 8645；未知商城不得猜测 ID。

### 决策输出校验

比较结果至少包含 `summary`、`best_sku_id`（允许为空）、comparison dimensions 和理由的 `evidence_ids`。每个 comparison dimension 只输出字段名及各候选对应的 evidence_id；展示值从服务端事实集读取，不接受模型返回的值。服务端校验：

- 每个 `evidence_id` 必须存在于该候选的服务端事实集中。
- 一个可展示的比较维度必须使用同一事实字段，且至少覆盖两个候选；展示值从对应 evidence record 读取。未知或冲突字段标成未知/冲突。
- `best_sku_id` 必须属于本轮候选，且至少有一个有效比较维度覆盖它与另一候选；否则 `best_sku_id` 置空。
- 结构校验失败时不创建推荐赢家；返回“当前证据不足以确定最优”，仍可展示候选和来源事实。

证据 ID 可验证来源引用存在，但不宣称能形式化证明任意自然语言句子的语义蕴含。评测需抽样检查推荐理由是否超出引用事实。

## 模型与上下文

- 保持 qwen-flash 负责轻量路由与简单条件抽取，qwen-plus 负责需求澄清与商品比较决策；订单时间解析优先使用确定性 Tool，模型只负责无法规则化的语义补全。
- 不以模型分层直接宣称 token 降低；对比上下文仅含预算过滤后最多 3 个候选、紧凑商品事实和引用 ID，订单统计上下文仅含结构化查询条件与聚合结果。token、成本、延迟均通过评测实测。
- 金额、商城、商品链接、商品字段、订单时间、统计数值和来源 ID 均不由模型生成。

## 可靠性与失败策略

- 值得买商品搜索失败：只对瞬时网络/服务端故障做指数退避重试；重试耗尽后返回可理解的失败，不静默切换到仿真商品。
- 订单 MCP 失败：对瞬时故障执行指数退避；重试耗尽后返回查询失败状态，不伪造空结果、不伪造统计值。
- `OPEN` 状态快速失败；冷却后仅允许一个 `HALF_OPEN` 探测；成功恢复 `CLOSED`，失败重新 `OPEN`。
- 所有 MCP 调用沿用 app lifespan 中 SourceRegistry 的保护包装与 Trace。无效参数、认证失败等非瞬时错误不做无意义重试。
- 模拟订单写入不套外部 MCP 重试。通过唯一幂等键使相同确认恢复/重放最多产生一条订单。
- 值得买商品搜索不可用时明确报错；订单 MCP 不可用时购物链路仍可用。

## 数据与订单

- `Order` 保留现有 conversation/user/SKU/平台/报价/成交价/状态字段；新增商品标题、商品 URL、数据源及商品快照，平台字段长度必须容纳商城原名。
- 用唯一 `order_intent_id` 作为模拟订单幂等键；金额以 Decimal 固化。旧订单新增快照字段允许为空。
- 用显式、可重复执行的数据库迁移升级既有 PostgreSQL。`Base.metadata.create_all` 不负责修改已存在表结构。
- 模拟下单状态仅从未确认进入 `cancelled`，或用户明确确认后进入 `placed`；确认前不写订单行。
- 订单查询沿用已落库的订单快照和成交金额；不会修改订单状态，不新增按订单号查询索引或接口。

## 前端与 API

- 候选卡展示真实商品、价格、商城及已有商品字段；比较表按候选和有证据的维度展示，不显示旧多平台报价表。
- 推荐摘要区显示首选和取舍理由；每条比较事实标出值得买来源。证据不足时如实展示，不强行标“最优”。
- 用户点选候选后点击“模拟下单”进入/提交 HITL 确认；取消不落订单。完成后展示模拟订单号、商品快照和确认时价格。
- 订单明细查询复用订单信息卡片，展示订单号、下单时间、商品名称、图片和成交价格；多笔结果按下单时间倒序排列。
- 消费统计展示总金额、订单数、平均客单价，以及请求指定的品类或平台分组；无结果时显示明确的空状态。
- 不提供订单号输入框、订单号搜索接口或多用户切换控件。
- 移除真实源“仅确认选择”端点流程；复用 `/resume` 的 confirm + `sku_id` 完成下单/取消。
- 不展示 `source_mode` 仿真比价切换，不保留仿真比价卡片作为用户功能。

## AgentState

在现有状态基础上增加订单查询所需字段：

```python
order_query: OrderQuery | None
order_results: list[OrderSnapshot]
order_summary: OrderSummary | None
order_clarification: str | None
```

不新增以下业务能力：

```text
order_number_query
user_scope
user_id 作为本期订单查询输入参数
```

## 验收与量化

- 离线单测不访问值得买网络；MCP schema/真实查询通过显式启用的 smoke/integration 测试验证。
- 检索测试覆盖商城映射、预算边界、缺价过滤、价格字段数值化与原始证据保留。
- 决策测试覆盖有效/无效 SKU、未知 `evidence_id`、事实值不一致、证据不足时不选赢家。
- 订单查询测试覆盖昨天/上周/最近 N 天/具体日期范围、关键词和平台筛选、明细查询、统计查询、空结果、歧义澄清及多轮条件隔离。
- 订单查询测试不包含订单号查询和多用户隔离场景，确保非目标不会被误实现。
- 下单测试覆盖确认/取消、所有权校验、订单商品快照、Decimal 金额、重复 resume 幂等。
- 混沌测试分别注入商品搜索和订单 MCP 故障；商品搜索故障不得产生仿真替代结果，订单 MCP 故障不得伪造空结果。
- 新增固定商品决策集和订单查询集，记录意图识别准确率、时间表达解析准确率、订单查询成功率、澄清后成功率、可比较候选覆盖率、证据引用合法率、理由越界抽检率、LLM token/成本、MCP P95、端到端 P50/P95；所有效果数字以实测结果回填 `docs/RESUME.md`，不将目标当成结果。

## 技术栈约束

- Python 3.12 + uv；FastAPI + SQLAlchemy 2.0 async + psycopg。
- Agent 使用 LangGraph 单 Agent StateGraph 与 PostgreSQL checkpointer。
- Qwen DashScope OpenAI-compatible；qwen-flash 路由/轻量抽取，qwen-plus 澄清/比较决策。
- PostgreSQL 16 存用户、会话、订单。
- MCP 使用 `mcp`、FastMCP、`langchain-mcp-adapters`；商品检索和订单分析能力通过 MCP 或标准 Tool 接入，业务节点不直接拼接外部服务请求。
- 可靠性使用 tenacity 指数退避、项目现有手写三态熔断与 OpenTelemetry/Langfuse。
- 前端保持 Vue 3 + Vite + TypeScript + Pinia，SFC 顺序为 template → script → style。
